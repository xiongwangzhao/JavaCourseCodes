# 履约域图一：模块-节点-能力矩阵

## 1. 系统定位

新履约服务是一个面向电商与零售履约场景的履约领域服务，统一承接订单进入履约链路后的核心业务能力，支撑商城、云店、欧Pos 三条业务线。

它的核心职责不是管理下游仓储系统、承运商系统或即时配送平台内部单据，而是：

- 以 `履约单` 作为唯一核心单据承接履约主链路
- 统一管理履约方式选择、履约时效计算、推单、发货、物流查询、拦截、转寄和物流状态更新
- 对接仓储、门店、承运商、即时配送平台等外部履约执行方
- 将外部异构履约进度统一映射为内部履约状态并沉淀到履约单

一句话概括：

**这是一个以履约单为履约主锚点，统一承接履约查询、履约执行与履约状态更新的履约域内核服务。**

---

## 2. 系统职责边界

### 2.1 本系统负责

- 配送方式查询
- 物流时效计算
- 物流查询
- 推单
- 发货
- 物流拦截
- 转寄
- 物流更新
- 履约单状态流转与轨迹留痕

### 2.2 本系统不负责

- 下游仓储系统内部作业过程
- 下游承运商系统内部运单执行过程
- 即时配送平台内部运力调度过程
- 发货单、配送单等下游单据的完整生命周期管理

说明：

- 发货单、配送单可以在下游系统中真实存在
- 本系统只关心它们对 `履约单` 产生的状态变化、外部单号和进度结果
- 本系统只沉淀自身的 `履约单` 及其轨迹、状态和外部引用信息

---

## 3. 业务线范围

履约域当前支持以下业务线：

- `商城`
- `云店`
- `欧Pos`

### 3.1 业务线差异摘要

| 维度 | 商城 | 云店 | 欧Pos |
| --- | --- | --- | --- |
| 主要履约方式 | 仓配快递为主 | 门店发货、即时配送、门店自提并存 | 即时配送、门店自提更常见 |
| 履约承接主体 | 仓储 / 承运商 | 门店 / 即时配送平台 / 仓储 | 门店 / 即时配送平台 |
| 物流查询重点 | 轨迹、包裹、签收 | 轨迹、骑手状态、自提进度 | 即时配送状态、自提 / 交付结果 |
| 状态更新来源 | 仓配系统、承运商 | 门店系统、即时配送平台、承运商 | 门店系统、即时配送平台 |

---

## 4. 业务场景划分

履约域一级业务场景先收敛为三类：

1. `仓配快递`
2. `即时配送`
3. `门店自提`

说明：

- `现场交付` 先收敛为 `门店自提` 的特殊交付路径
- `门店发货` 先收敛为履约来源，不单独上升为一级业务场景
- 图一只保留内核标准能力，不展开业务场景专属能力

---

## 5. 核心单据模型：履约单

### 5.1 单据定位

`履约单` 是履约域唯一核心业务单据，用于承接订单进入履约链路后的统一履约契约，记录：

- 这笔订单由谁履约
- 采用哪种履约方式
- 当前履约进度是什么
- 外部执行结果如何映射回内部状态

### 5.2 核心字段建议

| 字段分组 | 建议字段 | 说明 |
| --- | --- | --- |
| 主键与单号 | `fulfillment_order_id` | 履约单主键 |
|  | `fulfillment_order_no` | 履约单号 |
| 来源订单 | `source_order_id` | 来源订单号 |
|  | `source_order_type` | 来源订单类型 |
| 业务维度 | `biz_line` | 业务线：商城 / 云店 / 欧Pos |
|  | `scene_type` | 业务场景：仓配快递 / 即时配送 / 门店自提 |
|  | `fulfillment_source` | 履约来源：仓 / 门店 / 商家 |
| 收发信息 | `receiver_name`、`receiver_phone`、`receiver_address` | 收货 / 提货信息 |
| 主体信息 | `store_id`、`warehouse_id`、`merchant_id` | 履约承接主体信息 |
| 时效信息 | `expected_ship_time` | 预计发货时间 |
|  | `expected_delivery_time` | 预计送达 / 预计可提货时间 |
| 状态信息 | `fulfillment_status` | 履约单状态 |
|  | `latest_status_code` | 最新节点状态码 |
|  | `latest_status_desc` | 最新节点描述 |
| 外部引用 | `external_order_no` | 下游系统单号，可空 |
|  | `carrier_code` | 承运商 / 配送平台编码，可空 |
| 扩展信息 | `biz_ext` | 场景扩展字段 |
| 审计 | `created_at`、`updated_at` | 创建、更新时间 |

### 5.3 状态建议

建议至少支持：

- `INIT`
- `PUSHED`
- `WAIT_FULFILL`
- `FULFILLING`
- `WAIT_DELIVERY`
- `DELIVERING`
- `WAIT_PICKUP`
- `COMPLETED`
- `CANCELLED`
- `EXCEPTION`

说明：

- 不同业务场景会映射到不同子节点状态
- 但内核主状态统一沉淀在 `履约单` 上

履约域当前收敛为 8 个模块：

1. `配送方式查询`
2. `物流时效计算`
3. `物流查询`
4. `发货`
5. `推单`
6. `物流拦截`
7. `转寄`
8. `物流更新`

---

## 7. 图一建模口径

- 图一只描述**内核标准能力**
- 不出现 `仓配快递 / 即时配送 / 门店自提` 的专属能力
- 不把下游发货单、配送单建成内核主单据
- 所有执行、查询、更新结果最终都回写到 `履约单`

## 9. 设计结论

本版图一已经完成以下收敛：

- 只以 `履约单` 作为履约域唯一核心单据
- 不把发货单、配送单纳入内核主单据建模
- 图一只保留履约域内核标准能力
- 业务场景差异全部下沉到图二处理

履约域当前的一期内核模块统一收敛为：

1. `配送方式查询`
2. `物流时效计算`
3. `物流查询`
4. `发货`
5. `推单`
6. `物流拦截`
7. `转寄`
8. `物流更新`
