# 支付回调模块-节点矩阵

## 1. 模块定位

支付回调模块用于承接支付渠道的异步通知或统一回执，在一次请求中完成回调报文解析、支付单匹配、回调校验、支付结果落账、后置事件触发和回调响应返回。

支付回调回答两个问题：

- 这次渠道异步回调最终意味着这笔支付到了什么状态
- 回调结果如何准确落到账务主链路中的支付单与后续业务事件

---

## 2. 设计口径

### 2.1 模块边界

支付回调负责：

- 接收并解析渠道异步回调
- 匹配支付单和关联上下文
- 校验回调真实性与结果合法性
- 更新支付单最终状态
- 触发后置业务事件与补偿任务
- 返回渠道所需确认响应

支付回调不负责：

- 收银台支付方式编排
- 预支付创单
- 主动查单轮询
- 结算

### 2.2 前置原则

- 业务线与流程引擎在回调进入前，已完成渠道路由和支付场景标识沉淀
- 支付回调模块仅消费支付单与回调报文中已沉淀的业务场景信息
- 对不进入异步回调路径的场景，如 0 元支付、标准货到付款，通常不进入本模块

---

## 3. 执行编排总视图

```text
支付回调：
1. 接收回调数据
2. 查询支付单据
3. 识别回调特征
4. 校验回调结果
5. 更新支付结果
6. 结果更新后置处理
7. 返回回调响应
```

## 5. 统一上下文设计

### 5.1 统一上下文名称

建议在 `支付回调` 模块中维护统一的 `PaymentCallbackContext`，上下文中至少包含以下数据：

| 上下文数据项 | 数据说明 | 初始来源 |
| --- | --- | --- |
| `callbackPayload` | 原始回调报文、请求头、来源渠道等信息 | 渠道回调请求 |
| `callbackResult` | 标准化后的回调结果对象 | 接收回调数据节点 |
| `paymentOrder` | 回调命中的支付单 | 查询支付单据节点 |
| `paymentSnapshot` | 支付单中沉淀的场景快照、渠道快照、提交快照 | 查询支付单据节点 |
| `paymentFeatureSet` | 回调阶段、支付路径、渠道类型等统一特征 | 识别回调特征节点 |
| `paymentSceneSet` | 当前回调生效的业务场景集合 | 识别回调特征节点 |
| `callbackValidationResult` | 签名校验、金额校验、状态流转校验结果 | 校验回调结果节点 |
| `callbackTraceRecord` | 回调留痕记录 | 更新支付结果节点 |
| `postProcessPlan` | 支付结果落账后的后置处理计划 | 结果更新后置处理节点 |
| `callbackAck` | 返回给渠道的确认响应 | 返回回调响应节点 |
| `requestMeta` | 回调批次号、处理时间、链路标识等元数据 | 请求入口 |

### 5.2 上下文增量说明

| 节点名称 | 放入上下文的数据 | 说明 |
| --- | --- | --- |
| `接收回调数据` | `callbackPayload`、`callbackResult`、`requestMeta` | 装载并解析回调报文 |
| `查询支付单据` | `paymentOrder`、`paymentSnapshot` | 匹配支付单并装载支付快照 |
| `识别回调特征` | `paymentFeatureSet`、`paymentSceneSet` | 识别回调阶段与业务场景 |
| `校验回调结果` | `callbackValidationResult` | 完成签名、金额、状态流转等校验 |
| `更新支付结果` | 更新 `paymentOrder`、生成 `callbackTraceRecord` | 将回调结果正式落账并记录留痕 |
| `结果更新后置处理` | `postProcessPlan` | 生成事件、补偿和告警计划 |
| `返回回调响应` | `callbackAck` | 返回渠道要求的确认响应 |

## 6. 设计结论

本方案建议将支付域中的回调能力统一收敛为 `1 个模块`：

- `支付回调`

在设计上：

- 支付回调统一承接渠道异步通知
- 业务场景由支付单快照与流程引擎在前置阶段完成沉淀
- 回调模块内部不再设置“场景编排节点”
- 回调模块以支付单为锚点，完成结果匹配、校验和落账
- 成功、失败、关闭等结果在本模块内统一标准化，再触发后置事件与补偿
