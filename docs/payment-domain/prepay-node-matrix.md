# 预支付模块-节点矩阵

## 1. 模块定位

预支付模块用于承接收银台提交后的正式支付请求，在一次请求中完成支付请求装载、支付单构建、渠道路由、渠道预支付发起、预支付结果处理与结果返回。

预支付回答两个问题：

- 当前这笔支付请求应该走哪条渠道预支付路径
- 预支付完成后，应如何沉淀支付单并向前端返回可执行的支付结果

---

## 2. 设计口径

### 2.1 模块边界

预支付负责：

- 接收收银台提交指令
- 构建支付单
- 识别支付特征与业务场景
- 装载渠道约束
- 路由并发起渠道预支付
- 处理预支付同步结果
- 返回前端拉起支付所需信息

预支付不负责：

- 最终支付成功确认
- 异步支付回调落账
- 查单补偿
- 结算

### 2.2 前置原则

- 业务线与流程引擎在流程开始前已完成业务场景选择
- 预支付模块仅消费已生效的 `paymentSceneSet`
- 支付业务场景不在预支付模块内单独通过节点编排

---

## 3. 执行编排总视图

```text
预支付：
1. 查询支付请求
2. 识别支付特征
3. 装载渠道约束
4. 构建支付单
5. 发起渠道预支付
6. 处理预支付结果
7. 返回预支付结果
```

## 5. 统一上下文设计

### 5.1 统一上下文名称

建议在 `预支付` 模块中维护统一的 `PrepayContext`，上下文中至少包含以下数据：

| 上下文数据项 | 数据说明 | 初始来源 |
| --- | --- | --- |
| `submitInstruction` | 收银台提交的支付指令摘要 | 收银台 |
| `cashierSnapshot` | 收银会话快照、支付方式快照、场景快照 | 收银台 |
| `paymentTarget` | 本次预支付对应的支付对象 | 查询支付请求节点 |
| `payerProfile` | 付款用户、账户、实名等信息 | 用户域、账户域 |
| `merchantProfile` | 商户、门店、终端、组织主体等信息 | 组织域、门店域 |
| `terminalContext` | APP / H5 / 小程序 / PC / POS 等终端上下文 | 请求入口 |
| `paymentFeatureSet` | 支付阶段、支付组织方式、终端类型等统一特征 | 识别支付特征节点 |
| `paymentSceneSet` | 本次已生效的业务场景集合 | 识别支付特征节点 |
| `paymentConstraintSet` | 支付时效和交易约束集合 | 装载渠道约束节点 |
| `channelConstraintSet` | 渠道规则、产品码、受理限制等集合 | 装载渠道约束节点 |
| `riskConstraintSet` | 风控与准入约束集合 | 装载渠道约束节点 |
| `paymentOrder` | 本次生成的支付单 | 构建支付单节点 |
| `channelRouteResult` | 渠道路由结果 | 发起渠道预支付节点 |
| `channelRequest` | 发往渠道的标准请求对象 | 发起渠道预支付节点 |
| `channelResponse` | 渠道同步返回结果 | 发起渠道预支付节点 |
| `prepayResult` | 标准化后的预支付结果 | 处理预支付结果节点 |

### 5.2 上下文增量说明

| 节点名称 | 放入上下文的数据 | 说明 |
| --- | --- | --- |
| `查询支付请求` | `submitInstruction`、`cashierSnapshot`、`paymentTarget`、`payerProfile`、`merchantProfile`、`terminalContext`、`requestMeta` | 装载本次预支付处理所需的基础支付请求信息 |
| `识别支付特征` | `paymentFeatureSet`、`paymentSceneSet` | 识别支付特征与生效场景 |
| `装载渠道约束` | `paymentConstraintSet`、`channelConstraintSet`、`riskConstraintSet` | 装载支付、渠道与风控约束 |
| `构建支付单` | `paymentOrder` | 生成支付单并初始化状态 |

| `返回预支付结果` | `prepayResultView` | 组装返回结果 |

## 6. 支付单单据模型设计

### 6.1 单据定位

`支付单` 是预支付阶段的正式业务单据，用于承载一次支付请求的主事实，记录支付对象、支付方式、支付金额、支付阶段、预支付受理结果和后续支付状态演进。

### 6.2 设计原则

- 支付单在预支付阶段生成，是支付回调、查单、退款的主锚点
- 支付单记录“这笔钱为什么付、打算怎么付、当前付到什么状态”
- 同一支付对象在多次重试场景下，可通过支付单幂等控制和子级尝试记录扩展
- 一期先明确支付单主模型；支付尝试单可作为后续扩展

### 6.3 支付单核心字段建议

| 字段分组 | 建议字段 | 说明 |
| --- | --- | --- |
| 主键与单号 | `payment_order_id` | 支付单主键 |

| 支付对象 | `payment_target_type` | 支付对象类型 |
|  | `payment_target_id` | 支付对象编号 |
| 参与方 | `payer_id` | 付款用户 |
|  | `merchant_id` | 商户主体 |
|  | `store_id` | 门店主体，可空 |
|  | `terminal_id` | 终端主体，可空 |
| 金额 | `pay_amount` | 本次支付金额 |
|  | `currency` | 币种 |

|  | `channel_code` | 路由到的渠道编码，如 WECHAT / ALIPAY / UNIONPAY |

|  | `payment_scene_snapshot` | 生效场景快照，如组合支付、分期支付、国补支付等 |

|  | `updated_at` | 更新时间 |
| 扩展 | `biz_ext` | 扩展字段，用于存放低频业务透传字段 |

### 6.4 支付单状态建议

建议至少支持以下状态：

- `CREATED`：支付单已创建
- `PREPAYING`：正在发起预支付
- `WAIT_PAY`：预支付成功，等待用户完成支付
- `PAYING`：支付处理中
- `SUCCESS`：支付成功
- `FAILED`：支付失败
- `CLOSED`：支付关闭
- `CANCELLED`：支付取消

### 6.5 单据关系建议

```text
收银会话
  -> 支付单
  -> 渠道预支付结果
  -> 支付回调
```

说明：

- 一期可先由 `支付单` 直接承接预支付结果和回调结果
- 如后续需要增强重试、多次切换支付方式、渠道多次发起等能力，可增加 `支付尝试单`

## 7. 设计结论

本方案建议将支付域中的预支付能力统一收敛为 `1 个模块`：

- `预支付`

在设计上：

- 预支付承接收银台提交结果，负责构建支付单并发起渠道预支付
- 业务场景由业务线与流程引擎在入口前完成选择
- 预支付内部不再设置“场景编排节点”
- 预支付以 `支付单` 作为正式业务单据，承载本次支付请求和同步受理结果
- 最终支付成功与失败的确认，由支付回调模块继续承接
